# EXP-013 — Tool Selection on Real MCP Server Loadouts

**Status:** draft preregistration (2026-10-28); **approved 2026-10-28**; loadouts and cases committed; **blocked on gold validation**  
**Milestone:** M5 follow-up  
**Label:** all numbers below are plans. Nothing has been run.

---

## Question
On tool surfaces taken from real, published MCP servers, loaded together the way a user would, how often do models pick the wrong tool, and do the errors fall on tool pairs whose descriptions overlap?

## Why
EXP-009–012 found near-perfect selection whenever each tool states a distinct scope (`results/exp009_analysis.json`, `exp011_analysis.json`, `exp012_analysis.json`); the only order effect came from synonym tools (EXP-001 siblings, exploratory). Those surfaces were written by us. Real descriptions are the open question: if they overlap, the synonym result predicts errors there, and surfacelab's similarity check would be the right tool to find them.

## Hypotheses
- **H1 (confirmatory):** Across tool pairs within a loadout, the confusion rate (gold A, emitted B) is positively correlated with the description similarity of A and B (`surfacelab.similarity`, same embedding as EXP-004).
- **H2 (confirmatory):** Selection accuracy on real loadouts is lower than on the `nd_*` surfaces of EXP-009 (pooled 99.7%), by more than 5 pp, for at least one model.
- **H3 (exploratory):** Models agree on which cases they get wrong (errors are a property of the surface, not the model).

## Loadouts
Built from EXP-006 `tools/list` snapshots (verbatim names, descriptions and schemas), grouped so that servers plausibly compete:

| Loadout | Servers |
|---|---|
| browser | playwright (all 25 tools), chrome-devtools (navigation category: 6 tools) |
| web | fetch, tavily (all 5), brave-search (web, news, image search) |
| workspace | filesystem (all 14), github (10 repository and file tools via `--tools`) |
| docs | context7, aws-documentation, fetch |

Final loadouts are built by `scripts/build_exp013_loadouts.py` and committed as `fixtures/surfaces/real_*.json` before any case was written; dropped tools are listed under Deviations.

**Token budget rule.** The Groq free tier allows 8K tokens per minute per org, so a rendered loadout must stay under 6,000 tokens (`o200k_base`). A loadout over budget uses the server's own documented tool-selection option (e.g. GitHub `--toolsets`) to drop whole toolsets, chosen before any case is written; tools are never edited or truncated. The final loadouts and their token counts are committed before cases are written.

## Cases
12 per loadout (**48 families**, `fixtures/cases/real_loadouts.jsonl`), written from the snapshots. Each names a concrete task a user would ask for. At least half are written to sit near a likely overlap (e.g. "take a screenshot of example.com" on `browser`). Gold is validated blind by a second person before any run, as in ADR-023, and may hold several tools.

## Design

| Factor | Values |
|---|---|
| Models | `openai/gpt-oss-20b`, `openai/gpt-oss-120b`, `qwen/qwen3.8-27b` (Groq; checked 2026-10-28 to support forced tool calls at temperature 0) |
| Orderings | 2 per loadout: snapshot order, and servers reversed |
| Temperature | 0 |
| Refusals | recorded, scored incorrect |

Total 48 × 2 × 3 = **288 trials**.

## Primary outcome and analysis
- H1: Spearman ρ between pair similarity and pair confusion rate, over pairs with at least one gold occurrence; permutation test (10,000, seed 42), one-sided.
- H2: accuracy per model, clustered bootstrap over families; difference from the EXP-009 accuracy for that model (Qwen: from EXP-014).

## Verdict rule
- **H1 confirmed:** ρ > 0 with permutation p < 0.05 for at least one model (Holm across models).
- **H2 confirmed:** accuracy CI upper bound below (EXP-009 accuracy − 0.05) for at least one model.

## Reporting rule
Results describe description patterns (e.g. "two browser servers both describe a screenshot tool without saying how they differ"), never that a vendor's server is bad. Every example quoted is from a committed snapshot.

## Budget cap
`--max-usd 3.00` per model.

## Deviations
- **Token cap restated on provider counts.** The draft capped the local `o200k_base` count at 6,000. Groq counts tools differently per model (gpt-oss about 0.6x, Qwen about 1.05x the local count), and the Qwen input limit is 7,000. The cap is now **6,500 provider-reported prompt tokens for every model**; measured for Qwen: browser 6,232, web 5,828, workspace 5,402, docs 5,300; for gpt-oss 3,206 to 4,441 (`results/exp013_prompt_tokens.json`).
- **Loadouts narrowed to fit, using only each server's documented options; no tool was edited.** Dropped: the `data` loadout (only MongoDB probed ok, and it alone is 15.6K tokens); Notion (21.7K, no selection option); Firecrawl (16.6K, no selection option), so its search and scrape tools, which overlap Tavily, Brave and fetch, are not tested; `memory` from workspace; `git` (did not start). Chrome DevTools keeps only its navigation category, so its screenshot and snapshot tools, which overlap Playwright's, are not tested. These losses limit H1 to the overlaps that remain (navigation, tabs, waits, close; web search, news, extract; local vs GitHub files; AWS docs vs fetch vs Context7).
- Gold is multi-tool where both servers' tools do the job (e.g. rb01 navigate); validation may widen or narrow it.
