# EXP-003 — Single-Edit Tradeoff

**Status:** run and analysed. Every edit **inconclusive** for both models: the base surface is at 100% accuracy, so no edit can show an improvement (see Results)  
**Milestone:** M3  
**Label:** numbers in Results trace to `results/exp003_analysis.json` (from `scripts/analyze_exp003.py`, replay only).

---

## Question
For each description edit, what happens to selection accuracy?

## Hypotheses
- **H1 (confirmatory):** `add_usage_clause` improves accuracy vs base on `goodserver` for cases where the request matches the usage clause.
- **H2 (confirmatory):** `goodserver_set_desc_vague` (set_description to "Creates an event.") regresses accuracy for `create_calendar_event` cases.
- **H3 (exploratory):** `trim_to_first_sentence` does not significantly change accuracy when the first sentence is informative.

## Design

| Factor | Values |
|---|---|
| Base surface | `goodserver` |
| Edit surfaces | `goodserver_add_usage`, `goodserver_add_negation`, `goodserver_prepend_summary`, `goodserver_trim`, `goodserver_set_desc_vague` |
| Model | `openai/gpt-oss-20b` (Groq), `openai/gpt-oss-120b` (Groq) |
| Variants | canonical order only (edit is the treatment; order swept in EXP-001) |
| Cases | `fixtures/cases/core.jsonl` (15 families) |

Total: 15 × 6 surfaces × 2 models = **180 trials**

## Primary outcome
Paired accuracy delta vs base (McNemar, matched on case family), with clustered paired-difference CI. Reported per edit.

## Multiple comparisons
5 edits = 5 tests. Pre-declared family: {add_usage_clause, add_negation_clause, prepend_summary, trim_to_first_sentence, set_description}. Holm correction for confirmatory claims (H1 and H2 only). The remaining 3 edits are exploratory and labelled so.

## Overfitting guard
Edits evaluated on held-out families. Split: families c001–c010 are train (not used for evaluation); c011–c015 are evaluation. (In EXP-001 all families were used; here the edit was designed on the training split.)

## Verdict rule (per edit, pre-declared)
- **helps:** CI lower bound > +0.05 (5 pp improvement).
- **regresses:** CI upper bound < -0.05.
- **costs:** accuracy flat (CI contains 0) but description token count increased > 20%.
- **inconclusive:** otherwise.

Token delta computed exactly from `render.py` output on base vs edited surface.

## Budget cap
`--max-usd 2.00`

## Deviations
1. **Temperature 0** (`--temperature 0`); not specified in the plan. See EXP-001 deviation 1.
2. **The `trim` edit is a no-op.** `goodserver_trim.json` is identical to the base surface (descriptions unchanged, 96 tokens each), so H3 cannot be tested.
3. **The held-out split barely covers the edited tools.** Edits target one tool each: `add_usage` and `add_negation` change `get_weather`, `prepend_summary` changes `search_web`, `set_desc_vague` changes `create_calendar_event`. The evaluation split c011–c015 has one weather case (c011), one search case (c012), no calendar case, and three abstain cases. H1 therefore rests on 1 case per model and H2 has no held-out case at all. All 15 families are reported as exploratory.
4. **Edits were not designed on the training split.** They come from fixed templates in `scripts/gen_fixtures.py`, so the overfitting guard protects against nothing here.
5. **Token counts** use the `o200k_base` tokenizer over description text (the plan named `render.py` output without a tokenizer).

## Results
Temperature 0, canonical order, 15 families × 6 surfaces × 2 models = 180 trials, 0 errors. Delta = edit accuracy − base accuracy, clustered bootstrap over families (10,000 resamples, seed 42).

| Edit | Tool changed | Description tokens vs base | Held-out (c011–c015), both models | All 15, 20b | All 15, 120b |
|---|---|---|---|---|---|
| add_usage (H1) | get_weather | +19.8% | 100% → 100% | 100% → 100% | 100% → 100% |
| add_negation | get_weather | +14.6% | 100% → 100% | 100% → 100% | 100% → 100% |
| prepend_summary | search_web | +14.6% | 100% → 100% | 100% → 100% | 100% → 100% |
| trim | none (no-op) | 0% | 100% → 100% | 100% → 100% | 100% → 100% |
| set_desc_vague (H2) | create_calendar_event | −17.7% | 100% → 100% | 100% → 93.3% (−6.7 pp [−20.0, 0.0]) | 100% → 100% |

**Verdicts**
- **All edits: inconclusive** for both models. The base surface is already at 100%, so "helps" is impossible, and no edit moved held-out accuracy.
- **H1: not supported**, and not testable at this design: the model cannot improve on 100%.
- **H2: not testable on held-out data.** In the training split, 20b missed one calendar case (c010) under the vague description, the predicted direction, but one case is not evidence.
- **"costs" was not triggered:** `add_usage` adds 19.8% to description tokens, just under the 20% threshold.

To be informative, this experiment needs a base surface the models do not already solve, for example the `siblings` or `badserver` tools, with held-out cases for every edited tool.
